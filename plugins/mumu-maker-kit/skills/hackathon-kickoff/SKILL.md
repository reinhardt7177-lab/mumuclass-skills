# 해커톤 킥오프 — 한 가지를 완벽하게, 배포된 상태로

해커톤은 기능 3개를 반쯤 만드는 것보다 **1개를 완벽하게 시연**하는 쪽이 이긴다. 그리고 **처음 2시간 안에 배포된 상태**를 만들어 두는 팀이 끝까지 안정적이다.

## 0. 먼저 확인 (한 번에 묻기)
- 대회 시간, 팀 인원, 주제·심사 기준, 허용 도구(외부 API, 클라우드 배포, 회사 데이터 사용 가능 여부)
- 시연 환경: 노트북, 프로젝터, 태블릿, 전자칠판, 인터넷 여부

## 1. 주제 좁히기 (0~1시간)
- 문제 한 줄: "누가, 언제, 무엇 때문에 불편한가"
- **핵심 기능 딱 하나**와 시연 시나리오 3단계(들어온다 → 한다 → 결과에 놀란다)를 정한다.
- 아이디어 2~3개를 내고, 심사 기준에 비춰 추천 하나를 고른다.

## 2. 스택 고르기
- 고정된 스택은 없다. 앱 성격(2D/3D, 실시간, 로그인·데이터, 기기, 배포)을 따져 **후보 2~3개와 추천 1개**를 이유와 함께 제시한다.
- 해커톤에서는 "팀이 가장 빨리 배포할 수 있는가"를 큰 기준으로 둔다.

## 3. 첫 배포 (1~2시간)
- 빈 뼈대라도 **운영 주소가 뜨는 상태**를 먼저 만든다. (`ship-check` 스킬의 마무리 루틴)
- 시드 데이터(빈 화면 시연 금지)와 기본 화면 1장을 넣는다.

## 4. 핵심 기능 → 디자인
- 핵심 기능을 끝까지 완성한다. 자주 커밋하고 자주 배포한다.
- 디자인은 `craft-consult`로 방향 2~3개 중 하나를 고르고, 보여 주기 전에 `detail-qa`로 검수한다. 첫인상이 "와" 소리 나는 화면 1장에 집중한다.
- 교육용이면 `edu-content-writer`로 글·문제의 흐름과 위계를 잡는다.

## 5. 시연·발표 준비 (마지막 4시간)
- **백업 영상**: 시연이 실패할 때를 대비해 1~2분짜리 화면 녹화
- **발표 5장**: 문제 → 해결 → 데모 → 기대 효과 → 팀·다음 계획
- **리허설**: 시연 시나리오를 3번 그대로 해 본다. 인터넷이 끊겨도 되는지 확인한다.
- 운영 주소를 QR로 만들어 둔다.

## 시간표 예시 (24시간)
| 시간 | 할 일 |
|---|---|
| 0~1h | 주제·핵심 기능 1개·시연 시나리오 |
| 1~2h | 스택 결정, 뼈대, 첫 배포 |
| 2~16h | 핵심 기능 완성 (자주 커밋·배포) |
| 16~20h | 디자인·디테일 검수·시드 데이터 |
| 20~24h | 백업 영상, 발표 자료, 리허설 |

## 금지
- 기능 욕심으로 핵심 기능을 반만 만들기
- 마지막에 처음 배포하기
- 로컬에서만 되는 시연
- API 키를 코드나 발표 화면에 노출하기
